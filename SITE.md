# Wildmere Website

## Product and Design

A field guide to a real, playable indie prototype. The site invites visitors into Wildmere's quiet creative sandbox, shows actual captures, explains the controls, and makes the project's limits explicit. It is not a SaaS template, store, crowdfunding page, or promise of a finished game.

The design carries the game's forest green, warm cream, serif wordmark, and layered voxel symbol onto a paper-like editorial layout. A large landscape opens the page; numbered field notes, an eight-material palette, a dark controls section, and restrained technical disclosures give the long page a clear rhythm. Both desktop and mobile have purpose-built layouts.

## Tooling Choice

**Static semantic HTML + CSS + a small TypeScript enhancement, built with the existing Vite and Bun setup.** The website has no application framework and never imports Three.js. The original game remains a separate HTML entry at `/play/`.

- **Why not React, Next.js, or Svelte?** This is one information page, without authentication, user data, a CMS, or application state. Shipping a UI runtime and hydration for a palette and image viewer would add little value.
- **Why not Astro?** Astro would be a good choice for a larger content site. Here, adding another framework and build lifecycle to an existing Vite project is unnecessary. Static HTML already gives this one page immediate, indexable content.
- **Why not just unbundled HTML and CSS?** Reusing Vite gives us strict TypeScript, optimized assets, locally bundled fonts, hashed CSS/JS, development reloads, and one static build for both routes. No hand-maintained asset copies or second deployment are needed.
- **Why Sharp?** This build-only image processor converts the real PNG screenshots into responsive WebP files. It reduces the largest page assets substantially without shipping an image library to the browser.
- **Why Playwright and axe?** Playwright already exists in the project. The additional development-only axe integration checks accessibility issues in the actual page rather than claiming compliance from markup alone.

HTML owns the content, CSS owns the presentation, and TypeScript only enhances the material selector, native screenshot dialog, and mobile menu closing behavior. This keeps the simple approach maintainable without inventing a component framework.

## Implementation Plan and Files

The work was organized as: preserve and route the existing game; build the static content and visual identity; integrate real optimized images with missing-image fallbacks; add small accessible interactions; test desktop/mobile, production, accessibility and game regressions; document the outcomes.

| File                        | Role                                                                                                            |
| --------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `index.html`                | Complete website content, semantic sections, inline original icons, navigation and dialog                       |
| `src/site/style.css`        | Website-only layout, typography, focus treatments and responsive/reduced-motion styles                          |
| `src/site/main.ts`          | Material descriptions, image enlargement, and native mobile menu enhancement                                    |
| `play/index.html`           | Original game host relocated to `/play/`; existing game modules are unchanged                                   |
| `vite.config.ts`            | Separate website/game build entries, relative base, screenshot integration                                      |
| `scripts/site-images.ts`    | Real PNG detection, WebP optimization, development asset serving, production emission, labelled fallback markup |
| `scripts/site-checks.ts`    | Browser interaction, accessibility, responsive, no-JavaScript and isolation checks; website captures            |
| `scripts/screenshots.ts`    | Existing gameplay tests updated to visit `/play/`                                                               |
| `package.json`, `bun.lock`  | Bun scripts and locked build/test dependencies                                                                  |
| `README.md`, `SITE.md`      | Route update, setup, game/website documentation and trade-offs                                                  |
| `screenshots/website-*.png` | Real browser captures of the website, generated by `site:check`                                                 |

There is no game rewrite, WebGL embed, new server API, tracking, account form, or pretend mailing-list submission.

## Local Setup

```bash
bun install
bun run dev
```

Open `http://localhost:5173/` for the website and `http://localhost:5173/play/` for the game. Use the address printed by Vite if that port is already taken.

```bash
bun run check
bun run build
bun run preview
```

- `check`: strict TypeScript, Prettier checks, and the existing Bun game unit tests.
- `build`: TypeScript checking and a production build of **both** HTML entries into `dist/`.
- `preview`: static production preview, normally `http://localhost:4173/` and `/play/`.
- `format`: formats website/game source, configuration, HTML, scripts, and documentation.

## Screenshot Sources

Keep the real source captures at:

```text
screenshots/in-game.png
screenshots/main-menu.png
```

No manual move into `public/` is required. The Vite integration reads these at server/build startup, makes 720px and 1440px WebP variants at quality 83, and serves/emits them at `media/`. Original PNGs are not changed. Restart the dev server or rebuild after replacing captures. The current screenshots are 1440×900; use that ratio for replacements so the reserved layout remains appropriate.

The in-game image is the hero, with a responsive CSS crop; the gallery and enlarged view show the full capture. The gallery also shows the real main menu. All visible photographs have descriptive alt text. The small material illustrations and decorative icons are CSS/SVG artwork, not claimed game screenshots.

If either PNG is missing or unreadable, the corresponding frame becomes an explicit **Real game screenshot not available** panel with its expected filename. Capture-specific copy is adjusted too. This fallback is in the rendered HTML, works without JavaScript, and does not prevent a build. `WILDMERE_SCREENSHOTS_DIR` can point to a different source directory. On Linux, `/dev/null` can be used as an intentionally absent image directory to test the fallback without deleting files.

To regenerate source game screenshots:

```bash
bunx playwright install chromium
bun run screenshots
```

That command still tests actual gameplay and writes the original two PNGs. It now visits `/play/`.

## Website Checks and Captures

```bash
bun run site:check
bun run build
WILDMERE_PREVIEW=1 bun run site:check
WILDMERE_TEST_MISSING=1 bun run site:check
```

The script starts and stops its own server on **4176**. The game screenshot script uses **4175**. Leave those ports free. On Linux installations missing browser libraries, `bunx playwright install --with-deps chromium` can install the required dependencies and may request elevated privileges.

Normal website checks produce:

- `screenshots/website-hero.png`: desktop first screen, 1440×1000.
- `screenshots/website-desktop.png`: full desktop page.
- `screenshots/website-mobile-hero.png`: mobile first screen, 375×844.
- `screenshots/website-mobile.png`: full mobile page.

These are actual browser captures, not design mockups. Missing-image checks do not overwrite them. The production-preview flag uses the current `dist/`, so run `build` first. The missing-image flag is intended for the development check; production fallbacks must be built with the missing-image directory override.

The browser checks cover headings/sections, the keyboard skip link, image loading, screenshot dialog and focus return, palette state, technical disclosures, mobile navigation, layout overflow at 320/375/768/1440px, no-JavaScript content, and the absence of game/Three.js requests on the website. axe scans the desktop, mobile, and open dialog against WCAG 2 A/AA and 2.1 AA rules. Tests also collect uncaught browser errors.

## Accessibility

- Semantic header, named navigation regions, main, sections with headings, figures/captions, definition-list controls, and footer.
- A visible-on-focus skip link; keyboard focus outlines; real links for navigation and real buttons for actions.
- A native modal dialog with Escape dismissal, a named close button, focus containment, and focus return. The underlying links open the real image without JavaScript.
- Native `details`/`summary` controls for technical information and mobile navigation; no essential content depends on hovering or animation.
- Material selection exposes `aria-pressed` and updates a polite live description.
- Descriptive image alt text; decorative artwork is hidden from assistive technology.
- Darkened metadata colors after the contrast scan identified weak labels. Reduced-motion preference disables smooth scrolling and transitions.
- Core copy, screenshots, play links, and disclosures remain available without JavaScript. Palette descriptions and in-page image enlargement are enhancements.

An automated axe pass is not a declaration of full accessibility compliance. Screen-reader testing, browser zoom review, and testing with people using assistive technology remain useful follow-ups. Small editorial labels are supplemental; substantive copy and control instructions are larger. The linked game itself needs desktop visual navigation and mouse/keyboard input.

## Performance and Deployment

The website does **not** load the game renderer or game styles. Its production enhancement script is approximately **1 KB gzip**, plus Vite's approximately **0.4 KB gzip** shared module-preload helper. Website CSS is about **5.3 KB gzip**. The screenshot variants are approximately **39–43 KB at 720px** and **131–145 KB at 1440px**, rather than serving original PNGs. These figures are build output sizes, not a claim about Core Web Vitals or hardware speed.

The hero is eager and high priority. Gallery images are lazy-loaded. `srcset`/`sizes` let the browser choose an appropriate variant; explicit image dimensions and aspect-ratio containers reserve space. DM Sans is bundled locally with `font-display: swap`; Georgia supplies the display serif. There are no external font/API requests, videos, carousels, canvas animation, analytics, or framework hydration.

Deploy the complete **`dist/` directory** to an ordinary static host after `bun run build`. It contains `index.html`, `play/index.html`, `assets/`, and `media/`. A host that serves directory index files needs no SPA rewrite. Relative build paths and `./play/` links also support a subdirectory deployment, provided the URL uses the normal trailing slash. No server runtime or secret is required.

CSS/JS/fonts use Vite-hashed filenames. Screenshot variants have stable filenames: configure the host to revalidate `media/` after deployments rather than applying year-long immutable caching to them. A future content-heavy version could hash those names too.

Vite's existing large-chunk warning belongs to the separately loaded Three.js **game** bundle, not the marketing site. Do not mistake the total deployment size for the website's initial download.

## Limitations and Self-Critique

The page is intentionally a single static document, not a CMS. Replacing screenshots requires restarting Vite or rebuilding. The image pipeline is tailored to this project's two 16:10 captures; arbitrary aspect ratios should be accompanied by updated dimensions. If a host loses an image after a successful deployment, ordinary browser image failure behavior applies; the labelled fallback is a **build/start-time** safeguard, not a network retry system.

The strongest aspects are the continuity with the game, real screenshot use, clear content hierarchy, honest scope, and separation of the lightweight website from WebGL. The weakest are the limited variety of source photography, the text-heavy lower sections, and some small supplemental field-note labels. The landscape hero deliberately crops the original frame; visitors can open the full version. There is no gameplay video, newsletter, social feed, or invented community link because those assets/services do not exist.

The next useful improvements are new real screenshots showing a player-built structure and cave entrance, manual assistive-technology review, and deployment-specific canonical/Open Graph image URLs once a real domain is chosen. Localization or a static content framework becomes worthwhile if the site expands into multiple development posts or languages. No network performance score, cross-browser certification, or live deployment is claimed.
